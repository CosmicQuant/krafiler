# Plan: SQLite-Free Backend + Modular Cloud Run Architecture

## Goal
- Remove all SQLite/Kysely dead code from the backend
- Make Firestore the sole database
- Split into two dedicated Cloud Run services: **Compute API** and **KRA Worker**
- Move CRUD from REST API calls to direct Firestore with Security Rules
- Replace Cloud Tasks with Cloud Pub/Sub for job queueing

---

## Why We Still Need a Compute API (And What We Don't Need It For)

### What Is Already Client-Side (No Server Needed)
| Feature | Current State | Why No Server Needed |
|---|---|---|
| **User Auth** | Firebase Auth in frontend | ID tokens verified by `verifyAuth.ts` middleware. Main auth is already Firebase-native. |
| **CRUD: Clients** | `.firestore.ts` routes mounted | Frontend can use `onSnapshot` directly. Firestore Security Rules enforce `ownerUid`. |
| **CRUD: Employees** | `.firestore.ts` routes mounted | Same — direct Firestore reads/writes. |
| **CRUD: Attendance** | `.firestore.ts` routes mounted | Same. |
| **CRUD: Leave, Loans, Docs** | `.firestore.ts` routes mounted | Same. |
| **Job Status Polling** | `useJobListener.ts` already uses `onSnapshot` | Already real-time Firestore. No changes needed. |

### What Genuinely Needs a Server (Compute API Only)
| Endpoint | Why It Needs a Server |
|---|---|
| `POST /api/auth/employee/login` | Uses `bcryptjs` for password comparison and `jsonwebtoken` to sign employee portal tokens. Can't run in browser. |
| `POST /api/auth/employee/set-password` | Uses `bcryptjs.hash()`. Needs server. |
| `POST /api/payroll/calculate-preview` | ~400 lines of tax logic (SHA, NSSF, AHL, PAYE, proration, 1/3 rule, loans, overtime, attendance). Exposing this client-side risks tampering. |
| `POST /api/payroll/generate-unified` | Generates Excel/CSV/PDF/ZIP files. Needs Node.js libraries (`exceljs`, `pdfkit`, `archiver`, `adm-zip`). |
| `POST /api/payroll/finalize` | Creates `loan_transactions`, decrements `remainingInstallments`, validates 1/3 rule. Needs atomic writes + business logic. |
| `POST /api/payroll/rollback` | Reverses loan transactions, restores balances, deletes adjustments. Needs server-side consistency. |
| `POST /api/email/send-payslip` | Needs `SMTP_PASS` secret. Can't be in frontend. |
| `POST /api/tax/file-return` | Frontend can't publish to Pub/Sub (needs GCP credentials). Rate limiting (10/15min) must be enforced server-side. Input validation centralized here. |
| `POST /api/tax/filing-status/:jobId/cancel` | Updates Firestore `cancelRequestedAt`. Could theoretically be client-side, but we want a single audit point. |

**Bottom line:** The Compute API is a thin "compute gateway" with only ~9 endpoints. Everything else moves to direct Firestore.

**Routes kept (exact list):**
- `POST /api/auth/employee/login` — `bcryptjs` + `jsonwebtoken` employee portal login
- `POST /api/auth/employee/set-password` — `bcryptjs.hash()`

- `POST /api/payroll/calculate-preview` — Tax calculation engine
- `POST /api/payroll/generate-unified` — CSV/Excel/PDF/ZIP generation

- `POST /api/subscriptions/webhook` — Paystack webhook (public, no auth)
- `GET /api/receipts/*` — Serve receipt PDFs (auth-protected)

- All `/api/employees/*` → Frontend uses `onSnapshot` on `employees` collection

### 3.2 Service 2: `krafiler-worker` (KRA Automation Worker)
**Purpose:** ONLY Playwright KRA filing

**Routes:**
- `POST /process-job` (from Pub/Sub push subscription)
- `GET /health`

**What it does:**
1. Receives Pub/Sub push with `jobId`
2. Fetches job payload from Firestore
3. Runs Playwright automation (`processFilingJob`)
4. Writes progress + logs back to Firestore via `jobStore`
5. Uploads receipt/PRN to Cloud Storage
6. Returns 200 to Pub/Sub (acknowledgement)

**Dockerfile:**

- Keep Chromium installation
- Remove Express routes, CORS, rate-limit middleware
- Minimal Express app with just `/process-job` and `/health`

**New files:**
- `frontend/src/hooks/firestore/useFirestoreClients.ts`
  ```typescript
  import { collection, query, where, onSnapshot, addDoc, doc, updateDoc, deleteDoc } from 'firebase/firestore';
  import { db } from '../../lib/firebase';

  export function useFirestoreClients() {
      const [clients, setClients] = useState<ClientObligation[]>([]);
      useEffect(() => {
          const uid = auth.currentUser?.uid;
          if (!uid) return;
          const q = query(collection(db, 'clients'), where('ownerUid', '==', uid));
          return onSnapshot(q, (snap) => { setClients(snap.docs.map(...)) });
      }, []);
      return { clients, loading };
  }

  export async function createClient(data: any) { return addDoc(collection(db, 'clients'), { ...data, ownerUid: auth.currentUser!.uid }); }
  export async function updateClient(id: string, data: any) { return updateDoc(doc(db, 'clients', id), data); }
  export async function deleteClient(id: string) { return deleteDoc(doc(db, 'clients', id)); }
  ```

## Phase 5: Firestore Security Rules Update

### 5.1 Add Missing Collections
Current rules only cover: `users`, `clients`, `employees`, `payrollRuns`, `jobs`, `subscriptions`

**Add rules for:**
- `attendanceRecords`
- `leaveRequests`
- `loans`
- `loanTransactions`
- `documents`
- `departments`
- `workSchedules`
- `holidays`
- `auditLogs`
- `payrollAdjustments`

### 5.2 Update `clients` Rules
Allow the **worker** (Cloud Run service account) to update `lastFiled` and `status` fields. Currently only the owner can update.

```
match /clients/{clientId} {
    allow read: if isAuthenticated() && resource.data.ownerUid == request.auth.uid;
    allow create: if isAuthenticated() && request.resource.data.ownerUid == request.auth.uid && isActiveSubscription() && withinClientLimit();
    allow update: if (isAuthenticated() && resource.data.ownerUid == request.auth.uid) || isWorkerServiceAccount();
    allow delete: if isAuthenticated() && resource.data.ownerUid == request.auth.uid;
}
```

`isWorkerServiceAccount()` needs a custom claim or a specific service account UID. Alternatively, use a Cloud Function for worker writes.

### 5.3 Allow Worker to Write Job Logs
```
match /jobs/{jobId} {
    allow read: if isAuthenticated() && resource.data.ownerUid == request.auth.uid;
    allow create: if isAuthenticated() && request.resource.data.ownerUid == request.auth.uid;
    allow update: if isAuthenticated() && resource.data.ownerUid == request.auth.uid;
    // Worker writes are done via Admin SDK (bypass rules) — no change needed
}
```

**Important:** The worker uses `firebase-admin` (Admin SDK), which bypasses Security Rules entirely. So worker writes don't need rule changes. Only frontend direct writes need rules.

## Key Decisions & Trade-offs

| Decision | Rationale |
|---|---|
| **Pub/Sub instead of Cloud Tasks** | Simpler routing, no `WORKER_URL` config, native retry, dead-letter topics |
| **Two services instead of one** | API stays lightweight (~200MB), worker keeps heavy Playwright image (~2GB). Different scaling needs |
| **Keep Compute API for payroll** | Payroll engine is complex and needs secrets. Can't run in browser or Firestore rules |
| **Admin SDK bypasses Firestore rules** | Worker uses `firebase-admin` — this is by design. Rules only constrain frontend direct access |
| **Frontend uses Firebase SDK for CRUD** | Real-time updates, offline support, no CORS, no API proxy needed |
| **Keep `jobStore.ts`** | Already Firestore-native. Worker and API both use it. No changes needed |
